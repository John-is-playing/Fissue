## 问题描述

`ratekit` 所有金额相关 API 都用 `float`，且各自的舍入规则不一致，
导致同一笔账在不同调用路径下算出不同结果。这不是单点 bug，
而是缺少一层统一的「金额表示与舍入」约定。

## 具体不一致点

### 1. 舍入方向各异

| 函数 | 当前位置 | 规则 |
|---|---|---|
| `prorate` | `math.floor(raw*100)/100` | 向下取整（对用户有利时反而不利） |
| `refund` | `math.floor(raw*100)/100` | 向下取整 |
| `format_amount` | `f"{v:,.2f}"` | 四舍六入五成双（Python 默认） |
| `apply_tax` / `remove_tax` | 不舍入 | 保留全部浮点误差 |

同一笔 3.335 元的金额，在 `prorate` 里变 3.33，在 `format_amount` 里变 3.34。

### 2. 浮点累积误差

```python
from ratekit import apply_tax, remove_tax
apply_tax(remove_tax(113.0, 0.13), 0.13)   # 112.99999999999999
```

应当用 `Decimal` 或按分（整数最小单位）运算，否则对账永远收敛不了。

### 3. 缺少货币与精度元数据

- 没有「币种」概念：JPY 没有小数位（0 位），KRW 同理，BHD 有 3 位。
  当前 `format_amount` 一律 2 位。
- 没有「最小单位」（分 / 厘）约定，无法表达「四舍五入到分」vs「到厘」。

## 为什么需要设计决策（而非直接改）

修复方案互斥，各有代价，需要维护者拍板：

1. **全面改用 `Decimal`**：最准确，但会**改变所有公开 API 的返回类型**，
   调用方 `== float` 的比较会失效 —— 是**破坏性变更**。
2. **改用以分（整数）为内部表示**：性能好、无误差，
   但要重新定义每个 API 的入参出参，且要处理非 2 位精度币种。
3. **保持 float，只统一舍入**：改动最小，但不解决累积误差。
4. **是否引入 `money`/`py-moneyed` 等第三方库**：涉及新增运行时依赖与许可评估。

此外还需决定：

- 舍入模式统一为哪种？（银行家舍入 vs 四舍五入 vs 远离零）
- 是否算**语义化版本的重大变更**？要不要发 1.0？
- 是否提供兼容开关（如 `rounding="half_up"`、`units="cent"`）？

## 影响范围

- `money.py`、`tax.py`、`pct.py`、`prorate.py` 全部涉及
- `tests/` 下大量断言需要重写（浮点断言改成精确比较）
- README 的 API 表格要补精度与舍入说明
- 若是破坏性变更，需要迁移指南
