## 问题描述

`textkit` 的各个函数对「什么算空白」「什么算一个词」「什么算一个字符」的处理
**互不一致**，导致同一个输入在不同 API 下得出矛盾的结论。这不是单点 bug，
而是缺少一层统一的文本规范化约定。

## 具体不一致点

### 1. 空白定义不一致

| 输入 | 期望 | `word_count` | 说明 |
|---|---|---|---|
| `"a\u3000b"`（全角空格 U+3000） | 2 | ? | 全角空格是 Unicode 空白 |
| `"a\u00a0b"`（不换行空格 U+00A0） | 2 | ? | NBSP 是否算分隔符？ |
| `"a\tb"`（制表符） | 2 | ? | `split(" ")` 不切制表符 |
| `"a\nb"`（换行） | 2 | ? | `split(" ")` 不切换行 |

`textkit/stats.py` 用 `text.split(" ")`，只认**半角空格**；
而 `textkit/wrap.py` 用 `text.split()`，认**全部 Unicode 空白**。
两者对 `"a\tb"` 会给出矛盾的结果（一个算 1 个词，一个算 2 个词）。

### 2. 字符计数口径不一致

`char_count(text, ignore_spaces=True)` 用 `ch.isspace()` 判断空白，
于是把 U+3000、U+00A0、`\t`、`\n` 全都算作"空白"并跳过。
但 `word_count` 并不把这些当作分隔符。同一段文本，
`char_count` 认为"没有空白"，`word_count` 认为"是一个词"——语义冲突。

### 3. 截断与折行的边界处理不一

- `truncate` 按**字符数**截断（`len`），对 CJK 与 emoji 都算 1
- `wrap` 按**字符数**折行，但 CJK 字符显示宽度是 2 列
- 结果是 `wrap` 在终端里排版错乱（详见 feature 请求 #4）

### 4. Unicode 规范化缺失

组合字符序列（如 `"e" + U+0301` 与预组合的 `"é"`）在
`char_count` 里长度不同（2 vs 1），在 `slugify` 里产出不同 slug（`e-` vs `é`）。

## 为什么需要设计决策（而非直接改）

修复方案有多个互斥选项，各有代价，需要维护者拍板：

1. **改用 `str.split()`**：最简，但会**破坏 `word_count("hello  world") == 3`** 的既有行为
   （连续空格不再产生空词），是**破坏性变更**。
2. **引入 Unicode 规范化层**（NFKC）：能统一全角/半角与组合字符，
   但会改变输入文本本身，可能影响调用方对原文的假设。
3. **引入 `\p{White_Space}` 语义的显式空白集合**：语义最准确，
   但需要重新定义每个 API 的契约并更新文档与测试。
4. **是否依赖第三方库**（如 `regex`、`uniseg` 提供字素簇切分）：
   涉及新增运行时依赖，需要评估体积与许可。

此外还需决定：

- 这些变更是否算**语义化版本的重大变更**（需要 major bump）？
- 是否要提供兼容开关（如 `normalize="none"|"nfkc"`）？
- CJK 的"显示宽度"语义要不要进入库的核心（见 #4）？

## 影响范围

- `textkit/stats.py`、`textkit/wrap.py`、`textkit/slugify.py`、`textkit/truncate.py` 均涉及
- 需要同步更新 `tests/` 下多个测试的预期值
- 需要更新 README 的 API 表格与语义说明
- 若做破坏性变更，需要迁移说明

## 建议

先在本 issue 讨论确定口径（空白集合、规范化策略、是否破版），
再拆成若干可独立落地的子任务。**不宜直接改代码**。
