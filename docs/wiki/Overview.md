# 项目概览

> 本页回答三个问题：**Fissue 是什么**、**它怎么跑起来**、**它现在到底靠谱到什么程度**。
> 细节分别指路到[架构设计](Architecture.md)、[快速开始](Getting-Started.md)、[基准与可信度](Benchmark.md)。

---

## 1. 它解决什么问题

维护开源仓库最痛的不是写代码，而是**面对一堆 Issue/PR 不知道该先看哪个**：

- 这条 Issue 是真 Bug 还是用户用错了？
- 这是真需求还是重复提交 / 刷量？
- 这个 PR 真的修好了问题吗？合并会不会带崩？
- 哪些可以放心让 AI 先修，哪些必须人来判断？

Fissue 把「**分诊（triage）→ 验证 → 修复**」整条流程自动化，并把每一步的**评分理由与证据**留痕，
供人复核。它的核心主张是——

> **别信模型的自述，要看独立证据。**

落成三条可执行的原则：

1. 结论必须有**独立证据**：F2P（修复前失败、修复后通过）+ 仓库既有测试（回归门），而不是模型说"我修好了"。
2. 不可信的一切都在**沙盒**里跑：Issue 正文、外部 PR 代码、仓库自身代码、模型的输出。
3. **永不自动合并**：AI 只提 PR / 打标签给建议，合并由人在平台上手动完成。

## 2. 核心流程

```
                    ┌────────────────────────────────────────────┐
                    │  抓取 Issue / PR（四平台，增量）            │
                    └───────────────────┬────────────────────────┘
                                        ▼
                    ┌────────────────────────────────────────────┐
                    │  元数据预筛 → AI 分类：BUG / FEATURE         │
                    └───────┬────────────────────────┬───────────┘
                            ▼                        ▼
                   ┌─────────────────┐      ┌─────────────────┐
                   │   Issue · BUG   │      │ Issue · FEATURE │
                   └────────┬────────┘      └────────┬────────┘
                            ▼                        ▼
              ┌──────────────────────────┐   评估可行性 / 难度 / 必要性
              │ AI 评估修复难度 + 写验证器│          打标签
              │      → 验证队列           │           → 等开发者处理
              └────────────┬─────────────┘
                           ▼
                   沙盒执行器跑验证器
                           ▼
        ┌──────────────────────────────────────┐
        │ 攒够 N 条 或 队列空 → 整批交 AI       │
        │ 打 有效性 / 重要性 标签                │
        └──────────────┬───────────────────────┘
                       ▼
        ┌──────────────────────────────────────┐
        │ 难度低 + 重要性高 → AI Agent 修复      │
        │ 难度低 + 重要性低 → AI Agent 修复      │
        │ 其余 → 打标签，等开发者                │
        └──────────────┬───────────────────────┘
                       ▼
              fork 分支 → 提 PR（带 AI 标签）

                    ┌────────────────────────────────────────────┐
                    │                PR · BUG / FEATURE           │
                    └───────────────────┬────────────────────────┘
                                        ▼
                        判定提交者：开发者/社区 or AI
                                        ▼
                     找关联 Issue → AI 编写验证器 → 修复队列
                                        ▼
                沙盒：合并 PR + 跑验证器验证功能 → 结果入队列
                                        ▼
              攒够 N 条 或 队列空 → AI 判定能否合并 → 打标签
                                        ▼
                          等开发者手动合并
```

## 3. 四条流水线

用户定义的规则映射为**四条互不干扰**的路径（详见[架构设计](Architecture.md#2-四条流水线)）：

| 入口 | 分类 | 处理链路 | 终点 |
|---|---|---|---|
| Issue | BUG | 评测难度 → 生成验证器 → 沙盒 base 验证 → verify 队列 → 批量定论 | tier1/tier2 → 自动修复提 PR；其余打标签等开发者 |
| Issue | FEATURE | 评测可行性/难度/必要性 → 打标签 | 等开发者 |
| PR | BUG | 判提交者 → 找关联 Issue → 生成验证器 → 沙盒合并并验证 → fix_bug 队列 → 批量定论 | 打标签**建议**合并，等开发者手动合并 |
| PR | FEATURE | 同上，入 fix_feature 队列（共用沙盒） | 同上 |

## 4. 交付形态

| 形态 | 入口 | 用途 |
|---|---|---|
| CLI | `fissue <命令>` | 单次/脚本化驱动全流程 |
| Web 工作台 | `fissue web` | 浏览器里看总览 / 条目 / 队列 / 任务 / 监控仓库 / 设置 |
| REST API | 同 `fissue web`，`/api/v1` | 给脚本与 CI 用 |
| 常驻服务 | `fissue serve` | 增量扫描 + 队列调度 + 阈值通知（也可同进程带起 Web） |

## 5. 技术栈

| 项 | 选型 |
|---|---|
| 语言 | Python 3.10+（CI 矩阵：3.10 / 3.12 / 3.14） |
| 交付形态 | CLI（typer）+ Web（FastAPI + Jinja2）+ REST API + 常驻服务 |
| 抓取平台 | GitHub · Gitee · AtomGit · GitLab（含自建实例） |
| AI | 任意 OpenAI 兼容端点（DeepSeek / OpenAI / 通义 / Kimi / 本地 vLLM…） |
| 存储 | SQLite（默认，零依赖，也是开发期唯一实测过的路径）· PostgreSQL（可选，需显式配置；**尚未在真实运行中验证**）；可导出 JSON / Markdown |
| 沙盒 | Docker：禁网、限 CPU/内存/PID/时长、非 root、只读根、只挂隔离工作区、可走受控转发通道 |
| 配置 | `.env`（密钥）+ `config.yaml`（业务规则），另有 `config.local.yaml` 覆盖层 |

## 6. 它靠谱吗（结论摘要）

Fissue 自己也要接受与它要求别人相同的检验。[基准与可信度](Benchmark.md) 公开了在
**五套对抗性夹具（合计 60 Issue + 20 PR）**上的真实测量结果。摘要如下：

**站得住的**：

- **回归门在 3 套夹具上全部拦下**了「修好目标却弄坏别处」的假修复——这是 F2P 单独做不到的。
- 假修复（F2P 不成立）被识破；刷量、误报、设计偏好变更均被**拦在自动修复之外**。
- 重复检测能召回中文同义重复，且不误标「同源但非重复」。
- **真实提 PR 路径已端到端跑通**（2026-10-13）：`envkit#4` → PR #31、`lockkit#2` → PR #28；
  两处改动都只有源码文件、**未夹带验证器测试文件**。
- `pipekit` 的 Issue 侧自动修复 **7/7**：7 条待修条目**全部在 2~3 轮内产出补丁**。

**尚未测量 / 明确保留的**：

- **PostgreSQL 后端未在真跑里用过**——开发期全程 SQLite。
- **Gitee 的写操作未验证**（建 Issue 被平台限制挡住）；四个平台的**只读**链路已全部跑通，
  GitHub / 极狐 GitLab / AtomGit 的写操作已验证。
- tier 标定有**公开保留**的期望不一致：`envkit` 5 处、`lockkit` 4 处，且两者**方向相反**——
  这是阈值标定问题，不是「模型一律偏松 / 偏严」。

> 我们宁可把这些写出来，也不愿给一份「全部通过」的漂亮表格——那正是 Fissue 存在的意义所反对的事。
